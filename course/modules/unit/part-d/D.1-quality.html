Step D.1: Coverage and what not to test

Coverage tells you which lines of your code ran while the tests ran. Try it:

Coverage บอกว่าบรรทัดไหนของโค้ดคุณถูกรันตอนที่ test รัน ลองดู:

npm run coverage

The table lists every file in src with the percent of statements, branches, functions and lines that ran. Uncovered Line #s says which lines never ran: a test is missing there. Two things to keep in mind:

  • Coverage shows what is not tested, never that the rest is tested well. A test with no expect gives 100% and proves nothing. That is why this module also puts bugs into the code (mutation checks): the real question is "does a test fail when the code is wrong?".
  • Do not chase 100%. This project asks for 40%, which the main steps reach; the checkpoint exercises (which test dates.js, markDone and TaskItem) lift it above 90%. db.js is a stand-in that is always mocked, so it stays at 0% and that is fine.

What to test: rules and decisions (validation, sorting, who is overdue), error paths, and what a user sees and does. What not to test: libraries (React and Vitest are tested by their authors), plain getters, the exact HTML or class names, and the inner steps of a function (test what goes in and what comes out, not how).

Brittle tests fail for the wrong reason. Signs: it breaks when you only restyle or rename; it repeats the code under test line by line; it depends on the order of other tests or on today's date (use a fixed now, as in the checkpoint); it uses real network or a real database. A good test fails only when the behavior is wrong, and its name tells you what that behavior is.

ตารางแสดงทุกไฟล์ใน src พร้อมเปอร์เซ็นต์ของ statement, branch, function และ line ที่ถูกรัน Uncovered Line #s บอกบรรทัดที่ไม่เคยถูกรัน: ตรงนั้นขาด test สองสิ่งที่ต้องจำ:

  • coverage บอกสิ่งที่ ยังไม่ได้ ทดสอบ ไม่เคยบอกว่าส่วนที่เหลือทดสอบดี test ที่ไม่มี expect ให้ 100% แต่พิสูจน์อะไรไม่ได้ เพราะอย่างนี้ module นี้จึงใส่บั๊กลงในโค้ดด้วย (การตรวจแบบ mutation): คำถามจริงคือ "test ล้มไหมเมื่อโค้ดผิด?"
  • อย่าไล่ตาม 100% โปรเจกต์นี้ขอ 40% ซึ่งทำได้ด้วย step หลัก ส่วนโจทย์ใน checkpoint (ที่ทดสอบ dates.js, markDone และ TaskItem) ยกขึ้นไปเกิน 90% db.js เป็นตัวแทนที่ถูก mock เสมอ จึงอยู่ที่ 0% และไม่เป็นไร

สิ่งที่ควรทดสอบ: กฎและการตัดสินใจ (validation การเรียง ใครเกินกำหนด) error path และสิ่งที่ผู้ใช้เห็นและทำ สิ่งที่ไม่ควรทดสอบ: ไลบรารี (React และ Vitest มีผู้เขียนทดสอบอยู่แล้ว) getter ธรรมดา HTML หรือชื่อ class ตรงตัว และขั้นตอนภายในของฟังก์ชัน (ทดสอบสิ่งที่เข้าและสิ่งที่ออก ไม่ใช่วิธีทำ)

brittle test ล้มด้วยเหตุผลที่ผิด สัญญาณ: พังเมื่อแค่ปรับสไตล์หรือเปลี่ยนชื่อ ทำซ้ำโค้ดที่ทดสอบทีละบรรทัด ขึ้นกับลำดับของ test อื่นหรือวันที่ของวันนี้ (ใช้ now ตายตัวเหมือนใน checkpoint) ใช้เครือข่ายหรือฐานข้อมูลจริง test ที่ดีล้มเฉพาะเมื่อพฤติกรรมผิด และชื่อของมันบอกว่าพฤติกรรมนั้นคืออะไร

Hint
